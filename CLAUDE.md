## Commands

Package manager is pnpm (`pnpm-lock.yaml`, `pnpm-workspace.yaml`).

- `pnpm dev` — start Next.js dev server
- `pnpm build` / `pnpm start` — production build / serve
- `pnpm lint` — ESLint (flat config, `eslint.config.mjs`)
- `pnpm typecheck` — `next typegen && tsc --noEmit`; typegen writes the global route types (`PageProps`, `LayoutProps`) that a fresh checkout, like CI, does not have yet
- `pnpm format` — Prettier on all `ts`/`tsx`
- `pnpm db:migrate` — create and apply a migration on the local (Neon dev branch) database (`prisma migrate dev`)
- `pnpm db:deploy` — apply pending migrations (`prisma migrate deploy`); runs before `pnpm build` on Vercel via [vercel.json](vercel.json)
- `pnpm db:drift` — fails (exit 2) when `prisma/schema.prisma` and the migrations disagree: replays the migrations in the scratch database named by `SHADOW_DATABASE_URL` (CI creates `pcsilicon_shadow`; locally use an empty database that is not the app's) and diffs it with the schema. Only reads. CI runs it after `db:deploy`; `CHECK`s and triggers aren't compared ([spec 025](docs/specs/025-cart-single-items/spec.md))
- `pnpm db:generate` — regenerate the Prisma client (also runs on `postinstall` and at the start of `pnpm build`, since Vercel may restore cached dependencies without running `postinstall`)
- `pnpm db:seed` — validate the catalog parts and create the missing ones (about 150, see [spec 011](docs/specs/011-seed-150/spec.md); the first 60 are from [spec 005](docs/specs/005-expand-seed-catalog/spec.md)) into the local (Neon dev branch) database; **create-only** ([spec 045](docs/specs/045-admin-products-create-edit/spec.md)): categories, brands and parts that already exist, by slug or SKU, are never changed (name, description, specs, category, brand, weight, warranty, box contents, `isFeatured`, price, stock, status and slug all belong to Admin once a row exists), so re-seeding production never undoes an admin edit; to see a changed seed data file on an existing row, edit it in Admin or use `--reset` on a dev database. Writes no images at all ([spec 049](docs/specs/049-product-images-upload/spec.md)): a product without photos shows its category placeholder, derived from its category, so a re-seed can never bring a placeholder back after the owner removes every photo or touch a real one. Rejects a category slug that is a reserved top-level route ([lib/reserved-slugs.ts](lib/reserved-slugs.ts); add new top-level routes there). `pnpm db:seed --reset` truncates the catalog tables first, `Build`, `Cart`, `Order` and `Voucher` included (it deletes shared builds, carts, orders and vouchers), and is refused when `NODE_ENV` or `VERCEL_ENV` is `production`, when `DATABASE_URL` is on the host in `PRODUCTION_DATABASE_HOST`, or when that variable is not set (set it in `.env.local` to the production database's host; [lib/reset-guard.ts](lib/reset-guard.ts), [ADR 0007](docs/adr/0007-share-builds-as-content-addressed-snapshots.md)). A plain `pnpm db:seed` upserts by SKU and never deletes, so it keeps shared builds and carts. Prints the target host before writing. Runs on the dev database, in CI (before E2E), and once by hand on production (see [spec 004](docs/specs/004-product-list/spec.md), "Seeding production"); never part of a build or deploy `pnpm db:seed --accounts-only [--production]` creates only the demo user (`demo@pcsilicon.tech`, password `DEMO_ACCOUNT_PASSWORD`, at least 12 characters) when no user has that email, never changes an existing one, and touches no catalog table; unset, it says so and skips; refused with `--reset`; same production rule as the staff scripts. It also seeds the shipping rates (only when `ShippingRate` is empty) and the `StoreSettings` row (only when missing), never overwriting them ([spec 028](docs/specs/028-shipping-data-and-fee-rules/spec.md)). It inserts the three demo voucher codes (`WELCOME10`, `SAVE500`, `BUILD5000`) each only when its code is missing ([spec 037](docs/specs/037-vouchers-at-checkout/spec.md)).
- `pnpm images:placeholders` — regenerate the placeholder product images in `public/images/placeholders/` from lucide icons ([scripts/generate-placeholders.tsx](scripts/generate-placeholders.tsx)). The output is committed; run it only to change the artwork. The eight category files are what the storefront shows for a product with no photo; `box.svg` and `detail.svg` are no longer used by the seed
- `pnpm images:og` — regenerate the default link-preview image `public/images/og-default.png` (1200 × 630) from [scripts/generate-og-image.tsx](scripts/generate-og-image.tsx) with `next/og`. The output is committed; run it only to change the artwork
- `pnpm payments:check` — check the Xendit test account in `.env.local` ([scripts/xendit-check.ts](scripts/xendit-check.ts), [spec 031](docs/specs/031-pay-with-xendit/spec.md)): prints only whether `XENDIT_SECRET_KEY` has the test prefix, creates a ₱19.99 session expiring in 24 hours, prints Xendit's answer and cancels it (`--keep` leaves it open to try GCash and Maya). Never prints the key
- `pnpm webhook:replay <ps-…> [--event completed|expired] [--url http://localhost:3000]` — send a Xendit-format session webhook with the token from `.env.local` to a local server and print the HTTP status ([scripts/webhook-replay.ts](scripts/webhook-replay.ts), [spec 032](docs/specs/032-payment-webhooks/spec.md)); posts only to `localhost`, `127.0.0.1` or `[::1]` over `http`. The handler confirms with the gateway, so it marks Paid only for a session the gateway reports paid. `pnpm payments:check --read <ps-…>` reads a paid session and its payment
- `pnpm psgc:convert` — convert the PSA PSGC workbook `data/psgc/{PSGC_VERSION}.xlsx` into the address JSON in `data/psgc/json/{version}/` ([scripts/convert-psgc.ts](scripts/convert-psgc.ts), [spec 028](docs/specs/028-shipping-data-and-fee-rules/spec.md)). The output is committed; run it only for a new quarter or a rule change. It prints the counts, the largest file and every cleaned name, and stops on a row it can't place

- `pnpm test` / `pnpm test:watch` — Vitest unit tests, once / in watch mode. Pure: no database or env vars needed
- `pnpm test:db` — Vitest database integration tests (`*.db.test.ts`, helpers in `test-support/`), run against `TEST_DATABASE_URL` only (a local Docker Postgres from [docker-compose.yml](docker-compose.yml): `pnpm test:db:up` / `pnpm test:db:down`, `pnpm test:db:migrate`), never `DATABASE_URL`. The setup applies the migrations, prints the host it uses, and refuses to run when the URL is missing or on the app's host ([test-support/db-guard.ts](test-support/db-guard.ts)). The Postgres major version (18) is the same in Neon, `docker-compose.yml` and CI. CI creates `pcsilicon_test` in its throwaway Postgres
- `pnpm staff:create --email <e> --name <n> --role owner|staff` / `pnpm staff:set-password --email <e>` / `pnpm staff:disable --email <e>` (`staff:create --email <e> --enable` undoes a disable) — the only ways staff get an account, change a password or are blocked ([spec 039](docs/specs/039-staff-sign-in-admin-shell/spec.md), [docs/setup/admin-accounts.md](docs/setup/admin-accounts.md)). The password comes from a hidden prompt, or stdin when not a TTY; there is no password option. They print the target host first and refuse the production database (`PRODUCTION_DATABASE_HOST`, compared without Neon's `-pooler`) without `--production`, and `--production` on any other database; with `PRODUCTION_DATABASE_HOST` unset only a local database is accepted ([lib/auth/script-guard.ts](lib/auth/script-guard.ts))
- `pnpm test:e2e` — Playwright E2E tests (Chromium only); starts `pnpm dev`, or reuses a running dev server. The `setup` project signs in once per role for the `admin` project (`e2e/admin-*.spec.ts`), which needs the E2E accounts on the app's database (`E2E_ACCOUNT_PASSWORD`, `DEMO_ACCOUNT_PASSWORD`; [docs/setup/admin-accounts.md](docs/setup/admin-accounts.md)); the `chromium` project (everything else) does not. With `CI` set it serves the production build with `pnpm start`, so run `pnpm build` first. One-time setup: `pnpm exec playwright install chromium`

Unit tests are `*.test.ts`, colocated with the code they test (e.g. [prisma/seed/validate.test.ts](prisma/seed/validate.test.ts)). E2E tests are `e2e/*.spec.ts`; use role-based locators. Specs import `test` and `expect` from [e2e/test.ts](e2e/test.ts) (enforced by ESLint), which fails a test when React logs a missing-key warning; React only checks keys in development, so that guard works against `pnpm dev`, not CI's production build. CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) runs install, lint, typecheck, `db:deploy` and `db:seed` against a throwaway Postgres, unit tests, build and E2E on every PR and push to `main`; branch protection requires its `ci` job.

## Project

"PC Silicon": a Philippine PC-parts store whose differentiator is a guided PC Builder that blocks incompatible parts before checkout. Portfolio/capstone project; payments run in gateway sandbox mode only. The product requirements (personas, features, payment methods such as GCash/Maya/COD, admin panel, development-approach change rules) are in [docs/prd.md](docs/prd.md) — read it before building features. The MVP is desktop-first.

## Stack and architecture

- Next.js 16.4 App Router (`app/`), React 19, TypeScript, Tailwind CSS v4 (configured via `app/globals.css`, no tailwind config file). Next.js here has breaking changes versus common knowledge — consult `node_modules/next/dist/docs/` before writing Next-specific code (see AGENTS.md).
- UI is shadcn/ui with the `base-mira` style on **Base UI** (`@base-ui/react`), not Radix. Generated primitives live in `components/ui/`; add more with `pnpm dlx shadcn@latest add <component>`. Icons are `lucide-react`. Config in `components.json`.
- Path aliases: `@/components`, `@/lib`, `@/hooks`, `@/components/ui`. Use `cn()` from `@/lib/utils` for class merging.
- Database: Neon Postgres via Prisma 7 with `@prisma/adapter-pg`. Schema in [prisma/schema.prisma](prisma/schema.prisma), config in [prisma7.config.ts](prisma7.config.ts), client generated to `generated/prisma` (gitignored). The app uses the pooled `DATABASE_URL`; migrations use `DATABASE_URL_UNPOOLED`. Prices are integer centavos. `Product.effectivePrice` (the price the shopper pays, `COALESCE(salePrice, price)`) is kept by a database trigger: filter and sort by it, and **never write it from app code** ([ADR 0004](docs/adr/0004-effective-price-column-kept-by-trigger.md)). `Product.searchVector` (`Unsupported("tsvector")`, GIN-indexed) is kept the same way by triggers on `Product`, `Brand` and `Category`; never write it either. Keyword search matches it in one raw query in [lib/search.ts](lib/search.ts) (`getSearchScope`: the text as a bound parameter through the SQL function `search_query`, ranked with `ts_rank_cd`); everything after that is the typed listing code scoped to the matching ids. The SQL functions `search_normalize` (the one normalizer for products and queries) and `search_query` live in the `product_search` migration; changing them or the weights is a new migration plus a backfill ([ADR 0005](docs/adr/0005-search-vector-kept-by-trigger.md), [spec 014](docs/specs/014-search/spec.md)). Display prices with `formatPeso()` from `@/lib/format`, and stock with `getStockStatus()` / `stockStatusLabel` from `@/lib/stock`. Render product images with `ProductImage` from `@/components/product/product-image` (`next/image` in a square `bg-muted` box, with a labelled fallback when a product has none); always pass `sizes` with the rendered width. `ProductImage.url` holds a site path or an `https://` URL, so real images only change data ([spec 006](docs/specs/006-product-images/spec.md)); a product's own photos come from the owner ([spec 049](docs/specs/049-product-images-upload/spec.md), the "Product images" paragraph below), and one without any shows its category placeholder. Show products in lists (category, search, related) with `ProductCard` from `@/components/product/product-card`, loaded with `productCardSelect` and mapped with `toProductCardData` from `@/lib/products`; cards show a spec summary line built on the server from the fields whose `FieldMeta` has `summary` (`specSummary` in `lib/specs`), and no discount badge ([spec 016](docs/specs/016-home-page/spec.md)). The product page's "Similar products" come from `getRelatedProducts` in [lib/products.ts](lib/products.ts) (same category, available first, then closest in `effectivePrice`; a raw query orders the ids) and stream in behind `Suspense` with a skeleton, after `notFound()` and the redirect so those keep their HTTP status ([spec 015](docs/specs/015-related-products/spec.md)). A listing shows a `ListingTarget`: a category (`categoryTarget(slug)`) or a search (`searchTarget(raw)`, whose cleaned `q` is part of the target), and the listing components take the target. Listing URL state (sort, page, filters) is parsed and serialized only in [lib/listing-params.ts](lib/listing-params.ts): build links with `listingHref`, change a filter with `withFilter` (it goes back to page 1) or `clearFilters`, and non-canonical URLs redirect to it ([spec 008](docs/specs/008-category-listing/spec.md)). Each listing filter is a pure object in `lib/listing-filters/` (`parse`, `serialize`, `chips`, optional `normalize` and `facet`; no database imports, since client components use it) plus its database condition in `lib/listing-filters/server.ts`. The common ones (brand, price, in stock, on sale) are keyed in the `commonFilters` list; adding one is a new file, an entry in each, and a group in the sidebar ([spec 012](docs/specs/012-common-filters/spec.md)). Spec filters are generated, never hand-written: a field is filterable when its `FieldMeta` has a `filter` kind (`enum`, `values`, `range`, `boolean`, `contains`), and `listingFilters(slug)` gives a category's list (common filters, then spec filters in metadata order), so `parseListingParams`, `listingQuery`, `listingHref` and `isCanonicalQuery` take the target (`filtersFor(target)` gives its filter list; search results have Category, then the common filters, and no spec filters). "Best match" (`relevance`) is offered only for a search with a query (`sortsFor`, `defaultSort`). Spec conditions are Prisma's typed JSON path filters on `specs` (field names from the metadata, values as bound parameters; they don't use the GIN index), and options come from `loadFilterOptions` with counts that apply every other active filter ([spec 013](docs/specs/013-spec-filters/spec.md)). Price filters take whole pesos in the URL and compare against `effectivePrice`; cards show the sale price, the one filters and price sorts use. Per-request data (stock, prices, product lists): the page calls `await connection()` (from `next/server`) so it renders per request, not at build time. Shared, rarely changing data (the category menu): a function in `lib/` wrapped in `unstable_cache` with a named tag and a `revalidate` backstop, and every app write invalidates that tag ([ADR 0003](docs/adr/0003-cache-shared-data-with-tags.md)). The home page is static with `revalidate = 600`: its Featured products (`Product.isFeatured`, set by the seed), Deals and brands come from [lib/home.ts](lib/home.ts), cached under `PRODUCTS_TAG` (`"products"`) for 10 minutes, so every app write to products or brands must invalidate that tag too. SEO ([spec 017](docs/specs/017-seo/spec.md)): the root layout sets `metadataBase` from `NEXT_PUBLIC_SITE_URL`, so relative canonicals and Open Graph URLs become absolute; set a canonical per page, never in a layout (metadata merges shallowly, so every page without its own would inherit it). Build absolute URLs outside metadata (sitemap, JSON-LD) with `absoluteUrl(siteUrl, path)` from [lib/seo/urls.ts](lib/seo/urls.ts). Product and BreadcrumbList JSON-LD come from the pure builders in [lib/seo/json-ld.ts](lib/seo/json-ld.ts), rendered only through `JsonLd` (`components/seo/json-ld.tsx`), which escapes `<`, `>` and `&` so product text can't close the script; the price is `effectivePrice` and availability comes from `getStockStatus`, and there are no ratings or reviews. The product page's visible breadcrumbs and their JSON-LD are built from one array. Set Open Graph and Twitter tags with `socialMetadata` from [lib/seo/metadata.ts](lib/seo/metadata.ts) (a page's `openGraph` replaces the layout's whole block, so pages always pass an image; SVG product images fall back to the default PNG, since link-preview crawlers don't render SVG). `sitemap.xml` ([app/sitemap.ts](app/sitemap.ts), data from [lib/sitemap.ts](lib/sitemap.ts), cached under `PRODUCTS_TAG` and `CATEGORIES_TAG` for an hour) lists the home page, categories with an active product and active products, never filter, sort, page or search URLs; `robots.txt` disallows nothing on purpose, so crawlers can see the `noindex` tags. Previews are kept out of the index by the `X-Robots-Tag: noindex` header Vercel adds. Local env lives in `.env.local`, never `.env`.
- Import the Prisma client as `db` from `@/lib/db` and env vars as `env` from `@/lib/env` (validated with `@t3-oss/env-nextjs` + Zod at startup). Never read `process.env` directly in app code; add new variables to the schema in [lib/env.ts](lib/env.ts) and to `.env.example`.
- Product specs are JSONB (`Product.specs`), shaped by Zod schemas in [lib/specs/](lib/specs/), one file per builder category, linked to `Category` rows by slug through `builderCategories` in `lib/specs/registry.ts` ([ADR 0001](docs/adr/0001-store-specs-as-jsonb.md), [ADR 0002](docs/adr/0002-spec-schemas-in-code.md)). Validate every specs write with `validateSpecs()`; type reads with `Specs<C>`. Spec field names carry their unit (`tdpW`, `lengthMm`, `capacityGb`) and hold integers in base units. `lib/specs` must not import server-only code (the builder runs it in the browser). Seed data lives in `prisma/seed/data/` (entry point `prisma/seed.ts`). A spec field a compatibility rule reads (`FieldMeta.rules`) must be required, and every rule needs a tagged field in each category the PRD rules table lists ([lib/specs/rules-coverage.test.ts](lib/specs/rules-coverage.test.ts)).
- Compatibility rules live in [lib/builder/](lib/builder/) ([spec 018](docs/specs/018-compatibility-rules/spec.md), [spec 019](docs/specs/019-count-capacity-power-rules/spec.md)): pure TypeScript the browser and the server both run. An ESLint `no-restricted-imports` block keeps `lib/builder/**` and `lib/specs/**` free of the database, env, the generated Prisma client (enums included), `prisma/`, `server-only`, `next` and `react`; their tests reach seed parts through [test-support/seed-parts.ts](test-support/seed-parts.ts) (`seed`, `buildA`/`B`/`C`, `seedPart`, `fixturePart`). A `Build` maps each slot (a builder category slug) to `{ part, quantity }` entries, 1:1 with `BuildItem` rows: storage holds several drives (one entry per product), memory one kit with any quantity, every other slot one part. Untrusted builds (localStorage, share links, checkout) always go through `parseBuild` (Zod, ids only; repairs and reports `BuildChange`s) and then `assembleBuild` (attaches the loaded parts, drops missing or misplaced ones); `checkBuild` throws `InvalidBuildError` only on a malformed in-memory build, i.e. a bug. `checkBuild(build)` returns `{ rule, severity, parts, message }[]` (errors first, then PRD table order); `checkCandidate(build, slot, part, { replace? })` returns only the issues the candidate makes new or more severe than in the build with that slot empty (for storage, without the candidate's change), so a problem the build already has isn't blamed on every candidate (it replaces the part in one-part slots and memory; in storage it adds a drive, or replaces the one named in `replace`); `buildStatus(issues)` gives `ok` / `warnings` / `errors`. A rule is one file in `lib/builder/rules/`, listed in PRD order in `rules/index.ts` (a finding may override the rule's severity, as PSU wattage does); messages use full product names and format values with `specValue` / `specList` from `lib/builder/format.ts` (the spec table's labels and units). `estimateWattage(build)` gives `{ watts, psuWatts, loadPercent }` (nulls before a PSU is picked): (CPU `tdpW` + GPU `boardPowerW` + `OTHER_PARTS_ALLOWANCE_W`, which is 0) × 13 / 10, all in whole numbers, and the PSU wattage rule uses the same figure; keep power math in integers. `pnpm exec vitest bench --run --reporter=verbose` times the engine; it isn't part of `pnpm test` or CI.
- The builder page and Add to build ([spec 020](docs/specs/020-builder-page/spec.md)): the saved build is a Zustand store ([lib/build-state/store.ts](lib/build-state/store.ts), `buildStore`) persisted to `localStorage` under `pc-silicon-build` (version 1) holding only `BuildItem`s, never names, prices, stock or specs. Every read goes through `parseBuild` and `capProducts` (at most `MAX_BUILD_PRODUCTS`, 20 different products), and every action is ignored until the saved build has been read (`skipHydration`; `useBuild` in [hooks/use-build.ts](hooks/use-build.ts) reads it after mounting and follows other tabs through the `storage` event), so the server render and the first client render match. Prices, stock and specs come fresh from `GET /api/builder/parts?ids=` ([app/api/builder/parts/route.ts](app/api/builder/parts/route.ts), `getBuilderParts` in [lib/builder-parts.ts](lib/builder-parts.ts)): ids checked by `builderPartsQuerySchema` (400 otherwise), active builder parts only, `Cache-Control: no-store`. `useBuildParts` ([hooks/use-build-parts.ts](hooks/use-build-parts.ts)) asks only when an id isn't loaded yet and drops gone parts (with a notice) only after a successful response. **Only buyable parts (`isBuyable`: in stock or low stock, the `inStock` meaning) can be added to a build**; a saved part that stops being buyable stays, with a note and the summary's availability line. Add to build always adds one unit and asks before replacing (`planAdd` in [lib/build-state/plan-add.ts](lib/build-state/plan-add.ts)). Shopper copy for slots is `SLOT_COPY` ([lib/build-state/slots.ts](lib/build-state/slots.ts)). The E2E fixture in [e2e/test.ts](e2e/test.ts) also fails a test on a React hydration error, in dev and in production builds.
- The slot picker ([spec 021](docs/specs/021-slot-picker/spec.md), [ADR 0006](docs/adr/0006-filter-builder-candidates-in-memory.md)): "Choose", "Change" and "Add another drive" on `/builder` open a dialog ([components/builder/slot-picker.tsx](components/builder/slot-picker.tsx)) that loads every active part of the slot's category fresh from `GET /api/builder/candidates?slot=` ([app/api/builder/candidates/route.ts](app/api/builder/candidates/route.ts), `getBuilderCandidates` in [lib/builder-candidates.ts](lib/builder-candidates.ts); `slot` checked by `builderCandidatesQuerySchema`, exactly one of the eight slots, 400 otherwise; `Cache-Control: no-store`; `useCandidates` asks once per opening). Compatibility runs in the browser, never in SQL: `pickerList` ([lib/build-state/picker.ts](lib/build-state/picker.ts), pure) runs `checkCandidate` for every candidate and returns the groups (fits, fits with warnings, fits but not buyable, doesn't fit; **errors decide before stock**), sorted cheapest first, the "Current" / "In your build (×n)" markers, each card's action, the banner of errors no candidate fixes (spec 019 D9), and the empty states. The default list hides errors and parts that aren't buyable; "Show all" greys them with the reasons as text. Picking adds or replaces at once, with no "Replace?" dialog; only a part with errors asks first ("Add anyway"), and a part that isn't buyable can't be added at all. `replaceDrive` in the store changes one drive in place; `useBuildParts().addLoaded` shows the picked part with no request. `lib/build-state/picker.perf.test.ts` holds the 100 ms budget in CI (median of 20 runs under 50 ms). The server re-checks the build at checkout with the same engine. Picker candidates come from the same row mapping as the parts route (`builderPartSelect`, `toBuilderPartData`).
- Sharing a build ([spec 022](docs/specs/022-share-build/spec.md), [ADR 0007](docs/adr/0007-share-builds-as-content-addressed-snapshots.md)): `Build` / `BuildItem` rows are immutable snapshots of a build's items (slot, product, quantity), never names, prices, stock or specs. Identity is a hash the server computes: `canonicalItems` / `canonicalText` ([lib/builder/canonical.ts](lib/builder/canonical.ts); `[slot, productId, quantity]` sorted by slot name then product id, `JSON.stringify`) hashed by `contentHashOf` (SHA-256 hex, [lib/build-share-hash.ts](lib/build-share-hash.ts)). That form is stored, so changing it needs a new ADR. The slug is 10 random `a-z0-9` characters, never derived from the contents. `upsertBuildSnapshot(tx, items)` ([lib/build-snapshot.ts](lib/build-snapshot.ts)) is the one snapshot write, called by `shareBuild` ([lib/build-share.ts](lib/build-share.ts); the server action `shareBuildAction` only forwards to it) and by Add build to cart inside the cart's transaction: `shareInput` ([lib/build-state/share.ts](lib/build-state/share.ts)) rejects anything `parseBuild` would repair, more than 20 items and quantities above `MAX_SHARE_QUANTITY` (99), then every product must be active and in its own slot, then `upsertBuildSnapshot` in one transaction. It never raises a conflict inside a transaction (Postgres aborts it after any error, so catching P2002 can't work there): `INSERT … ON CONFLICT DO NOTHING RETURNING` with no conflict target, so a duplicate `contentHash` and a random `shareSlug` collision both come back as no row; it then selects the row by `contentHash`, or retries a new slug (three tries), and inserts the `BuildItem`s only for a new row. `BuildItem.productId` is `onDelete: Restrict`: retire products with `status`, never delete them. `TRUNCATE ... CASCADE` from `Product` empties `BuildItem` and `CartItem` but not `Build` or `Cart`, so every reset names both explicitly (`prisma/seed/write.ts`, `resetCatalog()`); add each new table of that kind there. `/builds/[slug]` ([app/(store)/builds/[slug]/page.tsx](app/(store)/builds/[slug]/page.tsx)) is per request (`connection()`, no `loading.tsx`, so unknown or malformed slugs keep their 404), `noindex`, with its own canonical, and not in the sitemap. `getSharedBuild` ([lib/shared-build.ts](lib/shared-build.ts)) reads prices, stock and specs fresh and returns a product that is no longer active as name and brand only; `sharedBuildView` ([lib/build-state/shared.ts](lib/build-state/shared.ts), pure) leaves such parts out of the total, power and checks, and shows "Incomplete" in place of "OK". Open in builder passes the server-built `openPlan` to the store's `load` action (it just navigates when the saved build's canonical items equal the snapshot's). The share link uses `window.location.origin`, not `NEXT_PUBLIC_SITE_URL`. No rate limiting yet ([#64](https://github.com/romulojr-dev/pc-ecommerce/issues/64)).

## Working rules

- Ask before creating git worktrees, symlinks or junctions, or changing anything in `node_modules`. Turbopack can't follow a linked `node_modules`, and removing a link carelessly can delete the real dependencies.
- No gateway or other network calls inside a database transaction. Read or call the outside service before the transaction opens, or after it commits, and keep the transaction to database work, so a slow service never holds a pooled connection or a row lock ([spec 032](docs/specs/032-payment-webhooks/spec.md), [spec 034](docs/specs/034-start-payment-outside-transaction/spec.md)).
